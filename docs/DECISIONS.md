# Implementation decisions

## September 29, 2026 — Studio 1.0 product-lead upgrade (current)

- The owner requested Astra's complete product/design/technical handoff for Sol, not full production implementation in this pass. The design reference is an inspectable static artifact; it is not application proof.
- Preserve the garment-first ambition and broaden the release to six meaningful presets across two qualified families. Earlier one-blouse-only scope below describes the proof phase and is superseded for the final release, not permission to show unsupported gallery cards.
- Keep the warm atelier identity; deepen forest contrast, enlarge the garment, collapse diagnostics and use focused phone sheets. Make gets its own step-first layout. No OpenAI affiliation or copied branding.
- No signup in Studio 1.0. Add private isolated guest sessions and transactional local SQLite, with backup/import and stale-tab recovery. Do not deploy local SQLite to a stateless host.
- Qualify pattern source, version, code/output rights and full geometry before production operations. Existing shoulder fragments remain illustrative. FreeSewing candidates are not qualified merely by being open source or looking similar.
- Three.js is a progressive educational construction renderer with piece/edge bindings. It does not simulate fabric drape or establish body fit.
- Photo input supports visible-feature analysis and confirmed matching to supported templates. It cannot promise hidden pattern reconstruction or body measurements.
- Fabric/layout, exact export and revision-specific making are part of the full target, not indefinite follow-ons. Physical and printed validation remain explicit release gates.
- Gemini selects bounded registered tools; server checks numerical validity and acceptance. Keep the empirically used <=30s per-request deadline within a <=120s active run budget. No paid fallback, implicit keep or arbitrary execution.
- Sanity owns shared relationships/methods/sources; Context owns maintained explanation. Preserve KB-only MCP plus separate exact reads. Demonstrate a correction affecting two looks and review the actual served entry.
- Prepare event-impact logic and a Sanity Function locally, without deployment. The app can compare fingerprints on requests without a hosted function.
- Replace conflicting current scope/PRD/spec/checklist/product/architecture/content-model documents; preserve historical evidence below and in Git. Do not rewrite learner history or pretend the repository began empty.

## Historical decisions (then-current; later decisions above take precedence)

## September 29, 2026 — Sanity isolation and proof boundaries

- The old Fit-first checklist is superseded by the approved garment-first sequence. The existing revision store and illustrative Fit/Fabric/Sew work remain foundations, while a connected Explore stage is the new first user experience. One fully supported blouse is more credible than an unsupported multi-garment gallery; other garments remain unselectable until their versioned graphs and operations are real.
- The development seed currently uses dotted Sanity document IDs. Because unauthenticated requests cannot read these published records, the application will use a dedicated read-only Stitches Viewer token for this local integration path. Keep the Editor token in the guarded seeder, never the browser, and do not widen dataset scope in code. A later ID migration would require preserving and revalidating references; it is not needed to establish the present proof.
- Context entries are navigable explanations, not the authority for exact assembly dependencies. An entry rebuild after the neckline source correction briefly emitted a misleading sequential arrow despite the source records describing parallel steps. A source-scoped manual Knowledge Base instruction corrected the served entry; the application still derives actionable prerequisites from the validated Content Lake graph. The live MCP probe checks both the corrected relation and this observed contradiction regression.
- The Explore construction note is available only in read-only Sanity-development mode after a current Content Lake fingerprint and actual `construction_sequence` MCP entry agree on the neckline pieces and parallel branches. A missing token, stale fingerprint, or conflicting generated summary leaves the direct assembly view usable but withholds the extra note. This makes Context consequential without letting prose override the graph.
- The agent preview uses the exact `fit_style_operations` path observed in `initial_context`, not a guessed hyphenated variant or a caller-supplied path. The owner confirmed a Google Free-tier project and the selected model's official pricing lists free input/output. Local live probes may run within that $0 scope, with one attempt, capped output, bounded feedback, and explicit timeout/quota failure states; the preview remains disabled by default for normal users.

- The drafting spike uses original TypeScript cubic-curve calculations instead of adapting an unexamined FreeSewing design. It is intentionally a fragment-level numerical check with `readiness: incomplete`; evaluating a licensed, maker-reviewed pattern family and sleeve-cap operation remains mandatory. FreeSewing's old GitHub monorepo is archived and points to Codeberg, so any future adapter will be assessed against its current design-specific code and terms.
- The preliminary Gemini session uses the official SDK's documented manual function-calling flow, retaining the full model `Content` with thought signature and matching function-call ID when it sends tool feedback. It permits only server-defined pattern-context and incomplete shoulder-spike tools. The SDK request has a short timeout, one attempt, and bounded output. The project will not start live inference merely because a key exists; the owner's paid-provider budget is zero and free-tier account status has not been verified.
- The visible provenance disclosure uses resolver-derived source and relationship data, so future Sanity edits can change the trail without changing UI copy. It shows review status prominently and keeps the source's prose subordinate to deterministic rule/geometry checks. Current screenshots are explicitly local fixture evidence.
- Live Sanity inspection is opt-in and read-only until reviewed pattern geometry and project persistence exist. Development accepts only Stitches `development` and illustrative mode; reviewed accepts only Stitches `production` and reviewed mode. The page never falls back to fixture content on a live failure, and the backend—not only the disabled button—refuses demo mutations while live inspection is selected.
- The first HTTP agent preview is intentionally local-only, disabled by default, and limited to illustrative Sanity-development knowledge with an actual Context KB read. It requires a long server-only bearer token and an explicit verified-zero-cost model flag before any provider call. It checks the caller's project revision and exact knowledge fingerprint, but the geometry remains an authored interaction fixture; the response is always non-accepting and never cut-ready. Reviewed-mode agent preview waits for version-bound, physically assessed geometry rather than reusing sample curves.

- Stitches uses its own Sanity project (`l4eeamth`) in organization `o3i0aqvqq`. The `development` public dataset is for illustrative content and integration tests. The separate `production` dataset remains empty until a reviewed pattern and sources exist. Crossgrade credentials and its dedicated dataset are not silently reused for Stitches writes.
- The product app reads a bounded, fixed set of parameterized GROQ queries using a published perspective and no CDN. The resolver validates document types, IDs, references, pattern-version consistency, prerequisite cycles, operation registration, and reviewed status before returning a content fingerprint and effect trail. Fixture and Sanity adapters use the same resolver. There is no model-authored GROQ or fallback from a failed live request to fixture content.
- A separate adapter calls Sanity's documented read-only Context MCP Knowledge Base tools. The project read/write tokens and organization Context Viewer token are distinct; a project token cannot stand in for the Context credential. A mock transport test is not a live KB result.
- The local Studio points only at `l4eeamth/development`. A dry-run-only-by-default seeder refuses any other project/dataset and uses a dedicated write token only with `--apply`. Illustrative records must not become reviewed or cut-ready merely because they are stored in Sanity.
- No public Studio/app deployment, final submission, billing enablement, or production dataset write has been authorized.
